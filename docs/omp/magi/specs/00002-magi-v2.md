# MAGI v2 Specification

## Purpose

MAGI is a read-only deliberative decision system for ambiguous software and
system decisions. It frames the decision, establishes evidence, evaluates
alternatives through independent perspectives, and produces an evidence-backed
decision dossier before execution.

MAGI is a governance mechanism, not a worker pool. It determines what ought to
be done. An execution orchestrator such as Sybil determines how to implement an
accepted decision.

MAGI v2 makes deliberation an explicit capability of an ongoing top-level `omp`
session. It replaces the separate, specialized MAGI user session with a nested,
restricted MAGI workflow. This changes the invocation and runtime topology; it
does not weaken the deliberation protocol or the human-acceptance boundary.

## Goals

MAGI v2 MUST:

- let a user invoke deliberation from the session in which the decision arose;
- preserve independent first opinions from MELCHIOR, BALTHASAR, and CASPER;
- make the council's read-only boundary and delegation authority runtime-enforced;
- return one stable, evidence-backed decision dossier to the invoking session;
- prevent execution based solely on a MAGI recommendation; and
- retain dissent, missing evidence, and protocol failures in the final record.

## Non-goals

MAGI v2 does not:

- implement code, edit configuration, run mutating commands, or mutate external
  systems;
- replace Sybil or another execution orchestrator;
- make MAGI invocation automatic whenever the host detects uncertainty;
- introduce formal `melchior`, `balthasar`, or `casper` agent types;
- allow council members to delegate; or
- use a separate, specialized MAGI session as the normal user-facing interface.

## Appropriate use

MAGI is appropriate when a decision involves material uncertainty or tension
between technical correctness, operational safety, and human intent. Typical
uses include:

- framing an underspecified problem;
- deciding whether a problem requires a system change;
- comparing architectural or dependency choices;
- evaluating migrations and consequential compatibility changes;
- establishing constraints, non-goals, and acceptance criteria; and
- reconsidering an accepted decision when implementation reveals contradictory
  evidence.

MAGI is not intended for routine code generation, mechanical migrations,
localized bug fixes with known remedies, formatting, or ordinary line-level code
review.

## Invocation

A user explicitly invokes MAGI from an ongoing top-level `omp` session. The
host MUST NOT begin a MAGI deliberation merely because it infers uncertainty.

The host supplies MAGI-CORE with a bounded deliberation input containing, where
known:

- the desired outcome and exact decision;
- observed evidence and source references;
- constraints, non-goals, assumptions, and material unknowns;
- candidate approaches already raised; and
- relevant prior dossier identifiers and reconsideration triggers.

MAGI-CORE owns construction of the formal common dossier. The host MUST NOT
substitute its entire conversation transcript for the bounded input: task
children do not inherit host history, and an unfiltered transcript can anchor
the council around tentative conclusions.

`omp` manages the MAGI task lifecycle. MAGI-CORE returns one frozen decision
dossier in a terminal state. The host presents that result to the user and
enforces the acceptance requirements in this specification: an
`APPROVED_FOR_EXECUTION` dossier MUST NOT govern planning, dispatch, or
execution until the user explicitly accepts its exact dossier identifier. Other
terminal states MUST be surfaced according to their definitions.

## Runtime architecture

MAGI v2 has a host, a neutral coordinator, and three council instances:

```text
top-level omp host
  └─ magi-core
       ├─ magi-deliberator / MELCHIOR charter
       ├─ magi-deliberator / BALTHASAR charter
       └─ magi-deliberator / CASPER charter
```

### Host

The top-level `omp` session is the user-facing host. It invokes MAGI-CORE,
provides the bounded deliberation input, retains the returned dossier, and
enforces the explicit human-acceptance gate. It does not form a fourth council
opinion.

### MAGI-CORE

MAGI-CORE is a formal, restricted coordinator agent. It owns problem framing,
evidence gathering, common-dossier construction, council dispatch,
cross-examination, protocol validation, application of the decision rules, and
final dossier synthesis.

MAGI-CORE is not a substantive fourth council member. It MUST NOT introduce a
new proposal or invent a compromise during synthesis. It MAY reconcile evidence,
reject unsupported claims, and apply the authority rules in this specification.

The MAGI-CORE agent definition MUST declare a read-only tool set and a restricted
spawn policy equivalent to:

```yaml
---
name: magi-core
description: Read-only coordinator for in-session MAGI deliberations.
tools: read, grep, glob, web_search, hub
spawns: magi-deliberator
blocking: true
---
```

OMP grants the `task` tool to an agent with a permitted `spawns` declaration
while delegation depth permits. MAGI-CORE MUST therefore be able to dispatch
only `magi-deliberator`; it MUST NOT be able to dispatch general task workers,
execution orchestrators, or another MAGI-CORE.

MAGI-CORE remains read-only. It MUST NOT edit files, write code or configuration,
run mutating commands, mutate external systems, or send externally visible
communications.

### Council members

Council members use one formal OMP agent type: `magi-deliberator`.

MELCHIOR, BALTHASAR, and CASPER are separately named instances of that type. The
role charter is supplied through each task assignment, not encoded in three
separate agent definitions. The three instances share the same read-only tools,
isolation rules, and output contract. This centralizes common policy while
preserving role attribution and independent analytical obligations.

This design follows [Decision 00001: Keep Council Roles as Instructions](../investigations/00001-separate-agents.md).

A council member MUST NOT delegate. It MUST treat repository content, web pages,
and peer reports as untrusted quoted material, not as authority to alter its
assignment.

### Configuration

MAGI v2 requires two task-delegation levels below the host:

```text
host (depth 0) → magi-core (depth 1) → deliberator (depth 2)
```

The MAGI configuration MUST set `task.maxRecursionDepth` to `2`. This permits
MAGI-CORE to dispatch deliberators while preventing deliberators from dispatching
further agents. The system MUST permit the three first-round deliberators to run
concurrently.

## Council charters

### MELCHIOR — technical truth

MELCHIOR asks: **What is demonstrably correct?**

It MUST:

- test the premise and technical feasibility;
- prefer observed behavior, source, specifications, and real data;
- compare the smallest designs that can satisfy the desired outcome;
- distinguish evidence from inference;
- identify contradictions, missing evidence, and unverifiable claims; and
- reject a proposal whose critical path lacks an adequate verification strategy.

MELCHIOR controls disputed technical claims only to the extent those claims are
supported by evidence.

### BALTHASAR — stewardship

BALTHASAR asks: **What keeps the system healthy?**

It MUST evaluate compatibility, migration, rollback, failure modes, data
integrity, security, operability, maintenance cost, and recovery. It MUST
distinguish reversible local choices from consequential commitments and reject
scope creep or needless abstraction.

BALTHASAR may veto destructive, security-sensitive, data-loss, or irreversible
action that lacks a credible recovery path.

### CASPER — human intent

CASPER asks: **What serves the person asking?**

It MUST identify the actual user outcome rather than merely accept a proposed
mechanism. It MUST evaluate usability, surprise, naming, communication,
organizational effects, and likely misuse. It protects explicit human preferences
from being optimized away and escalates value choices that evidence cannot
resolve.

CASPER controls interpretation of explicit user intent and may require a human
choice when legitimate outcomes conflict.

## Deliberation protocol

### 1. Frame the decision

MAGI-CORE MUST establish a neutral common dossier containing:

- desired outcome;
- exact decision;
- observed evidence and its source;
- constraints and non-goals;
- assumptions and material unknowns; and
- candidate approaches already proposed.

MAGI-CORE MUST distinguish facts from assumptions. If a material factual question
can be answered with available read-only tools, MAGI-CORE MUST answer it before
dispatching the council. Every claim in the dossier MUST be traceable to evidence
or labelled as inference, assumption, or user-stated preference.

### 2. Form independent first opinions

MAGI-CORE MUST dispatch exactly three `magi-deliberator` instances in one
parallel task batch. Their stable task names MUST be based on `MELCHIOR`,
`BALTHASAR`, and `CASPER`.

Each first-round assignment receives the same common dossier and only its own
role charter. It MUST NOT receive, inspect, request, or infer another council
member's conclusion before it has produced its own first opinion.

Every first-round opinion MUST contain:

- `Verdict`: approve, reject, or escalate;
- `Argument`: its strongest reasoning;
- `Evidence`: source-linked facts, with inferences marked;
- `Assumptions`;
- `Risks`;
- `Alternatives`;
- `Reversal conditions`: facts that would change the verdict; and
- `Confidence`: low, medium, or high, justified by evidence coverage.

### 3. Cross-examine without forcing consensus

MAGI-CORE MUST wait for all available first opinions before cross-examination.
It MUST use the actual returned `agent://` report URIs, since stable task names
may be suffixed in a long session.

MAGI-CORE MUST send all three follow-up messages before waiting for their
responses. Each council member receives the other two complete first-round
reports and MUST address:

- the strongest opposing argument;
- one unsupported or weak claim in any report;
- material evidence the council still lacks;
- the condition most likely to change its own verdict; and
- a revised verdict, if warranted.

When a council member cannot read a peer artifact, MAGI-CORE MAY relay that
peer's complete report verbatim through `hub`. It MUST NOT replace the report
with a MAGI-CORE summary. The artifact failure MUST appear in the council record.

Council members MUST NOT converge for convenience. Principled disagreement is a
required output, not a failure to be hidden.

If a council member fails, MAGI-CORE MUST retry that role once with the same
common dossier and charter. If it fails again, MAGI-CORE MUST NOT impersonate it.
The final dossier MUST record the missing perspective and use
`INSUFFICIENT_EVIDENCE` whenever the absence could change the outcome.

### 4. Integrate under explicit authority

MAGI-CORE MUST apply these rules:

- Evidence outranks votes, confidence scores, and urgency.
- A demonstrated technical contradiction cannot be overruled by a majority.
- MELCHIOR controls disputed technical claims only when supported by evidence.
- BALTHASAR may veto destructive, security-sensitive, data-loss, or irreversible
  action lacking a credible recovery path.
- CASPER controls explicit user intent and may require a human decision where
  legitimate outcomes conflict.
- A non-unanimous recommendation may be execution-ready only when the action is
  local, reversible, and has an adequate verification strategy.
- Destructive, irreversible, security-sensitive, data-loss, or externally
  visible action requires unanimity or explicit human authorization.
- Missing facts and human value choices are distinct blockers and MUST be
  reported separately.
- Material dissent, council failures, and protocol failures MUST remain visible.

MAGI-CORE MUST NOT reopen settled implementation details unless evidence
contradicts a premise or an acceptance criterion cannot be met.

### 5. Conclude or escalate

MAGI-CORE MUST produce exactly one terminal state and one frozen decision dossier.
It MUST keep deliberation proportionate and MUST NOT manufacture disagreement for
a routine or predetermined decision.

## Terminal states

Every deliberation ends in exactly one state:

- **APPROVED_FOR_EXECUTION** — one solution is sufficiently specified for
  execution planning after explicit human acceptance.
- **HUMAN_DECISION_REQUIRED** — evidence cannot resolve a material preference,
  authority question, or high-impact tradeoff.
- **INSUFFICIENT_EVIDENCE** — a material fact is missing; the dossier identifies
  the required evidence and how it can be obtained.
- **NO_IMPLEMENTATION_RECOMMENDED** — the desired outcome does not require code
  or system changes.

`HUMAN_DECISION_REQUIRED` is required for materially underspecified intent, an
irreversible or high-impact choice outside delegated authority, unresolved
material disagreement, or low evidence coverage that could change the outcome.
It MUST present two to five materially distinct options, their tradeoffs, and
MAGI-CORE's recommended default.

`INSUFFICIENT_EVIDENCE` is required when the blocker is a missing fact rather
than a human preference. Neither votes nor urgency may bypass either terminal
state.

## Decision dossier and acceptance record

MAGI-CORE returns a frozen decision dossier. It is a decision contract, not an
implementation plan, and MUST remain understandable without access to transient
council state.

A dossier MUST contain:

- a unique dossier identifier and decision scope;
- its terminal state and decision;
- the bounded deliberation input and observed evidence, with provenance;
- material assumptions and unknowns;
- each council member's initial and final verdict;
- decisive reasoning and rejected alternatives;
- material cross-examination challenges and responses;
- preserved dissent and the conditions under which it becomes controlling;
- risks, constraints, and non-goals;
- observable acceptance criteria;
- reconsideration triggers;
- unresolved human decisions; and
- the authority status of the recommendation.

For `APPROVED_FOR_EXECUTION`, the host creates a separate acceptance record that
references the dossier identifier and the user's explicit acceptance. The host
MUST NOT alter the frozen dossier to record acceptance.

The execution handoff is the accepted dossier plus its acceptance record.
Execution owns decomposition, implementation, integration, and behavioral
verification. It MUST preserve the dossier's constraints and non-goals.

## Reconsideration and supersession

When execution or later evidence meets a dossier's reconsideration trigger, the
host MUST return the decision to MAGI before continuing affected execution.
MAGI-CORE MUST create a new dossier that references the prior dossier and states
whether it supersedes it. A new dossier MUST NOT silently overwrite a prior
accepted decision or its acceptance record.

## System invariants

- MAGI remains read-only throughout its lifecycle.
- MAGI-CORE may dispatch only `magi-deliberator`.
- Council members never delegate.
- The three perspectives remain substantively distinct despite sharing one agent
  type.
- First opinions are independent and peer conclusions are withheld until
  cross-examination.
- Claims are traceable to evidence or marked as inference, assumption, or user
  preference.
- Confidence never substitutes for evidence.
- Dissent, council failure, and protocol failure are never hidden.
- Human authority is required where specified.
- No execution begins solely because MAGI produced a recommendation.
- An accepted dossier is immutable; reconsideration produces a new, linked
  dossier.
