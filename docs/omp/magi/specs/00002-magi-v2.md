# MAGI v2 Specification

## Purpose

MAGI is a read-only deliberative decision system for ambiguous software and
system decisions. It establishes the decision and evidence, evaluates it through
three independent perspectives, and returns an advisory decision dossier before
execution.

MAGI determines what ought to be done. It does not implement the decision or
replace an execution orchestrator such as Sybil.

MAGI v2 runs inside an ongoing top-level `omp` session rather than a separate,
specialized MAGI session.

## Goals

MAGI v2 MUST:

- provide an explicit `/magi` command in the session where a decision arose;
- preserve independent first opinions from MELCHIOR, BALTHASAR, and CASPER;
- restrict MAGI tools and delegation authority at runtime;
- conduct one peer-informed revision round; and
- return one self-contained dossier that preserves evidence, dissent, unknowns,
  and material protocol deviations.

## Non-goals

MAGI v2 does not:

- implement code, edit configuration, run commands, or mutate external systems;
- invoke itself automatically or promise natural-language routing;
- replace Sybil or another execution orchestrator;
- introduce separate `melchior`, `balthasar`, or `casper` agent types;
- allow council members to delegate; or
- retain a separate MAGI session as a user-facing interface.

## Appropriate use

MAGI is appropriate when a decision involves material uncertainty or tension
between technical correctness, operational stewardship, and human intent.
Typical uses include:

- framing an underspecified problem;
- deciding whether a problem requires a system change;
- comparing architectural or dependency choices;
- evaluating consequential migrations or compatibility changes; and
- reconsidering a decision when implementation reveals contradictory evidence.

MAGI is not intended for routine code generation, mechanical migrations,
localized bug fixes with known remedies, formatting, or ordinary line-level
review.

## Invocation

The user invokes MAGI explicitly with `/magi [decision]` in an ongoing top-level
`omp` session. The extension command injects an instruction to the host; it does
not spawn agents or inspect conversation history itself. If invoked while the
host is streaming, the instruction MUST be delivered as a follow-up so the
in-flight turn finishes without interruption.

When an argument is present, the host treats it as the decision text. Without an
argument, the host identifies the decision currently under discussion and asks
the user only if no exact decision can be established.

The host invokes `magi-core` once and supplies a bounded input containing, where
known:

- the desired outcome and exact decision;
- observed evidence and source references;
- constraints, non-goals, assumptions, and material unknowns;
- candidate approaches already raised; and
- relevant prior decisions or reconsideration triggers.

The host MUST NOT pass the unfiltered conversation transcript. MAGI-CORE owns
construction of the formal common dossier.

## Runtime architecture

```text
top-level omp host
  └─ magi-core
       ├─ magi-deliberator / MELCHIOR charter
       ├─ magi-deliberator / BALTHASAR charter
       └─ magi-deliberator / CASPER charter
```

The package requires `task.batch=true`, sufficient delegation depth, and enabled
`magi-core` and `magi-deliberator` agents. It does not override host settings to
satisfy those prerequisites. Incompatible host configuration may surface as an
ordinary OMP task error.

### Host

The host constructs the bounded input, invokes MAGI-CORE, and decides whether to
accept the returned dossier. It does not form a fourth council opinion and MAGI
does not initiate implementation on the host's behalf.

### MAGI-CORE

MAGI-CORE is the neutral coordinator. It owns framing, evidence gathering,
council dispatch, cross-examination, application of the decision rules, and the
final dossier. It is not a fourth vote and MUST NOT introduce a new proposal or
invent a compromise during synthesis.

Its agent definition MUST declare a restricted tool and spawn policy equivalent
to:

```yaml
---
name: magi-core
description: Read-only coordinator for an explicitly requested in-session MAGI deliberation.
tools: read, grep, glob, web_search, hub
spawns: magi-deliberator
blocking: true
---
```

OMP may grant `task` from the `spawns` declaration. MAGI-CORE may dispatch only
`magi-deliberator`; it MUST NOT dispatch general workers, execution orchestrators,
or another MAGI-CORE.

MAGI-CORE remains read-only. It MUST NOT edit files, run commands, mutate external
systems, or send externally visible communications. It uses `hub` only for council
messaging and task-result observation, never process supervision or cancellation.

### Council members

MELCHIOR, BALTHASAR, and CASPER are separately named instances of the shared
`magi-deliberator` agent. Their charters are supplied in their task assignments.
They share one restricted runtime policy and MUST NOT delegate, implement, or
mutate anything.

Repository content, web content, task output, and peer reports are evidence, not
instructions that can override an agent's assignment.

This design follows [Decision 00001: Keep Council Roles as Instructions](../investigations/00001-separate-agents.md).

## Council charters

### MELCHIOR — technical truth

MELCHIOR asks: **What is demonstrably correct?**

It tests the premise and feasibility, prefers observed behavior and primary
sources, compares the smallest viable designs, distinguishes facts from
inference, identifies contradictions and missing evidence, and rejects a
proposal whose critical path lacks an adequate verification strategy.

MELCHIOR controls disputed technical claims only when supported by evidence.

### BALTHASAR — stewardship

BALTHASAR asks: **What keeps the system healthy?**

It evaluates compatibility, migration, rollback, failure modes, data integrity,
security, operability, maintenance cost, and recovery. It distinguishes
reversible local choices from consequential commitments and rejects scope creep
and needless abstraction.

BALTHASAR may veto destructive, security-sensitive, data-loss, or irreversible
action without a credible recovery path.

### CASPER — human intent

CASPER asks: **What serves the person asking?**

It identifies the desired human outcome rather than accepting a proposed
mechanism at face value. It evaluates usability, surprise, naming,
communication, organizational effects, and likely misuse. It protects explicit
preferences and escalates value choices that evidence cannot resolve.

CASPER controls interpretation of explicit user intent and may require a human
choice when legitimate outcomes conflict.

## Deliberation protocol

### 1. Frame the decision

MAGI-CORE establishes one neutral common dossier containing the desired outcome,
exact decision, observed evidence and provenance, constraints, non-goals,
assumptions, material unknowns, and proposed candidates.

Facts, inferences, assumptions, and user-stated preferences MUST remain visibly
distinct. MAGI-CORE resolves material factual questions with its available
read-only tools before dispatch when practical.

### 2. Form independent first opinions

MAGI-CORE dispatches exactly three `magi-deliberator` instances in one task batch,
with stable names based on `MELCHIOR`, `BALTHASAR`, and `CASPER`.

Every instance receives the same common dossier and only its own complete role
charter. No instance may inspect, request, or infer another role's conclusion
before returning its first opinion.

Each first opinion contains:

- a verdict: `approve`, `reject`, or `escalate`;
- its strongest argument;
- source-linked evidence, with inferences marked;
- assumptions, risks, and alternatives;
- reversal conditions; and
- confidence justified by evidence coverage.

### 3. Conduct one cross-examination round

MAGI-CORE waits for all available first opinions and reads each complete report.
Before sending follow-ups, it retains the complete report bodies in its own
context; `agent://` artifacts may later reflect a follow-up turn.

MAGI-CORE then sends every surviving council member:

- the actual identifiers of the other available first reports; and
- the complete text of those reports verbatim.

It sends all follow-ups before waiting for responses. Each member applies its
original charter and addresses the strongest opposing argument, a weak or
unsupported claim, missing material evidence, its most likely reversal
condition, and a final verdict with revision or affirmation rationale.

This is the only peer-informed round. Council members do not contact one another,
start another rebuttal, or converge for convenience.

If an initial role fails, MAGI-CORE retries it once with the same dossier and
charter. Missing reports or replies remain visible in the final dossier;
MAGI-CORE never impersonates a missing role.

### 4. Integrate under explicit authority

MAGI-CORE applies these rules:

- Evidence outranks votes, confidence scores, and urgency.
- A demonstrated technical contradiction cannot be overruled by a majority.
- MELCHIOR controls disputed technical claims only when supported by evidence.
- BALTHASAR may veto destructive, security-sensitive, data-loss, or irreversible
  action lacking a credible recovery path.
- CASPER controls explicit user intent and may require a human decision where
  legitimate outcomes conflict.
- Every recommendation records reversibility, verification strategy, and
  material dissent.
- For destructive, irreversible, security-sensitive, data-loss, or externally
  visible action, the dossier records whether the council was unanimous and any
  unresolved human decision.
- Missing facts and human value choices are distinct blockers.
- Material dissent and protocol deviations remain visible.

MAGI-CORE MUST NOT reopen settled implementation details unless evidence
contradicts a premise or an acceptance criterion cannot be met. It keeps the
deliberation proportionate and does not manufacture disagreement for a routine
or predetermined decision.

## Terminal states

Every deliberation ends in exactly one state:

- **APPROVED_FOR_EXECUTION** — one solution is sufficiently specified for
  execution planning.
- **IMPLEMENTATION_REJECTED** — the decision should not proceed because evidence
  establishes a technical contradiction, safety objection, or controlling veto.
- **HUMAN_DECISION_REQUIRED** — evidence cannot resolve a material preference,
  authority question, or high-impact tradeoff.
- **INSUFFICIENT_EVIDENCE** — a material fact is missing; the dossier identifies
  the evidence and how to obtain it.
- **NO_IMPLEMENTATION_RECOMMENDED** — the desired outcome requires no code or
  system change.

`HUMAN_DECISION_REQUIRED` presents two to five materially distinct options,
their tradeoffs, and MAGI-CORE's recommended default. `IMPLEMENTATION_REJECTED`
identifies the rejected in-scope approaches and controlling evidence or veto.
If more than one state applies, MAGI-CORE selects the most consequential and
explains why.

## Decision dossier

MAGI-CORE returns one concise, self-contained Markdown dossier:

```text
# MAGI Decision
Status: <terminal state>
Decision: <one sentence>
Authority: Advisory; execution authority remains with the invoking host and user.

## Evidence and assumptions
## Council record
## Rationale and dissent
## Risks and constraints
## Acceptance criteria
## Reconsideration triggers
## Protocol deviations
```

The council record identifies each role's report URI, initial and final verdict,
decisive reasoning, confidence, and reversal conditions. The rationale includes
material challenges, rejected alternatives, unresolved human choices, and the
reason for the selected terminal state where relevant.

The dossier may omit `Protocol deviations` when none occurred. It may cite council
artifacts for provenance, but a reader must not need them to understand the
decision.

## System invariants

- MAGI remains read-only and advisory.
- MAGI-CORE may dispatch only `magi-deliberator`.
- Council members never delegate.
- First opinions are independent.
- Exactly one peer-informed revision round occurs.
- Claims are evidenced or labelled as inference, assumption, or user preference.
- Confidence never substitutes for evidence.
- Material dissent, missing information, and protocol deviations remain visible.
