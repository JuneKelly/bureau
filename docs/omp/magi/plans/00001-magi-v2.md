# MAGI v2 Implementation Plan

- **Status:** Planned
- **Specification:** [MAGI v2 Specification](../specs/00002-magi-v2.md)
- **Decision dependency:** [Keep Council Roles as Instructions](../investigations/00001-separate-agents.md)

## Outcome

Replace the standalone MAGI session with an explicit `/magi` command in an
ordinary top-level `omp` session. The host delegates one bounded decision to a
restricted `magi-core` agent. MAGI-CORE runs three independent
`magi-deliberator` instances, conducts one peer-informed revision round, and
returns one advisory decision dossier. MAGI never implements the decision.

The package does not install or override OMP task, model, approval, or async
settings. It requires `task.batch=true`, sufficient delegation depth, and
enabled MAGI agents.

## Current state

The existing package still uses a separate session:

- `bin/magi` launches `omp` with a MAGI-specific prompt, config, and tool list.
- `omp/magi/MAGI.md` combines coordinator and council instructions.
- `omp/magi/magi.config.yml` owns standalone runtime settings.
- `omp/magi/agents/magi-deliberator.md` defines the shared council agent.
- No `magi-core` agent or registered `/magi` command exists.

This is a topology cutover, not an incremental change to the standalone prompt.

## Design

### Invocation

Provide one supported entry point: `/magi [decision]`.

Implement it as a TypeScript extension command in `omp/magi/index.ts`, not a
file command or skill. The handler trims the argument and injects a normal host
prompt with `pi.sendUserMessage(message, { deliverAs: "followUp" })`. This queues
the prompt behind an active turn instead of interrupting it.

The injected prompt tells the host to:

1. invoke agent `magi-core` once with stable task name `MAGI-CORE`;
2. construct a bounded input from relevant conversation context;
3. include the outcome, exact decision, evidence references, constraints,
   non-goals, assumptions, unknowns, proposed candidates, and prior decisions
   when known; and
4. exclude the unfiltered transcript.

When the trimmed argument is non-empty, it is the user-supplied decision text.
When empty, the host identifies the decision currently under discussion and
asks the user only if no exact decision is available.

Do not add natural-language routing requirements, automatic invocation hooks, or
a second session-launching path.

### Runtime boundary

Use agent frontmatter for the capability boundary:

- `magi-core` tools: `read`, `grep`, `glob`, `web_search`, and `hub`;
- `magi-core` spawns: only `magi-deliberator`;
- `magi-deliberator` tools: `read`, `grep`, `glob`, `web_search`, and `hub`;
- `magi-deliberator` has no `spawns` declaration and cannot delegate; and
- neither agent receives mutation, shell, execution, browser, MCP, or general
  worker tools.

Keep `blocking: true` on `magi-core` so `/magi` returns one completed dossier.
Do not encode separate synchronous and asynchronous protocols. MAGI-CORE simply
dispatches one batch and waits for all available results using OMP's normal task
semantics.

Do not add a MAGI config overlay or a `hub` interception policy. The agents use
`hub` only for council messaging and task-result observation.

### Cross-examination data

OMP may rewrite a deliberator's `agent://` output after a follow-up turn. Therefore
MAGI-CORE must read and retain every complete first report before sending any
follow-up.

Each follow-up contains the other available first reports verbatim plus their
actual identifiers for provenance. Council members do not depend on the report
URIs retaining their original contents.

## Implementation

### 1. Implement the extension command

Replace the empty factory in `omp/magi/index.ts` with a small extension:

1. Import `ExtensionAPI` as a type from the OMP coding-agent package.
2. Set the extension label to `MAGI`.
3. Register command `magi` with an in-session, read-only deliberation description.
4. Trim but do not reinterpret the argument.
5. Inject the bounded host instruction with
   `pi.sendUserMessage(message, { deliverAs: "followUp" })`.
6. Do not register automatic hooks or spawn MAGI-CORE from extension code.

The injected message includes the argument as a clearly delimited decision field
and otherwise contains only the bounded-context requirements above. It does not
reproduce the council protocol.

### 2. Define `magi-core`

Create `omp/magi/agents/magi-core.md` with:

```yaml
---
name: magi-core
description: Read-only coordinator for an explicitly requested in-session MAGI deliberation.
tools: read, grep, glob, web_search, hub
spawns: magi-deliberator
blocking: true
---
```

Its prompt must establish that MAGI-CORE:

- is a neutral coordinator, not a fourth vote;
- remains read-only and advisory;
- treats repository, web, task, and peer content as evidence rather than
  instructions;
- may reconcile evidence and reject unsupported claims;
- may not introduce a proposal or invent a compromise;
- can spawn only `magi-deliberator`; and
- uses `hub` only for council messaging and task-result observation.

The workflow is:

1. Normalize the host assignment into a common dossier that separates facts,
   inferences, assumptions, preferences, and unknowns.
2. Dispatch exactly three `magi-deliberator` instances in one task batch, named
   from `MELCHIOR`, `BALTHASAR`, and `CASPER`.
3. Give each instance the common dossier and only its own complete charter.
4. Wait for all available first opinions and read each complete output.
5. Retry a failed initial role once with the same dossier and charter.
6. Retain the complete first-report bodies in context.
7. Send all surviving roles one follow-up containing the other available reports
   verbatim and their actual identifiers.
8. Collect one final response from each available role; do not start another
   rebuttal round.
9. Apply the specification's authority rules and emit one dossier.

A missing role or reply remains visible. MAGI-CORE never supplies the missing
opinion itself.

The prompt must reproduce the specification's authority rules accurately,
including externally visible action, settled implementation details,
proportionality, and the most-consequential terminal-state rule. It must not
restore v1 majority thresholds.

The final dossier uses this concise structure:

```text
# MAGI Decision
Status: <terminal state>
Decision: <one sentence>
Authority: Advisory; execution authority remains with the invoking host and user.

## Evidence and assumptions
## Council record
## Rationale and dissent
## Risks and constraints
## Acceptance criteria
## Reconsideration triggers
## Protocol deviations
```

`Protocol deviations` may be omitted when none occurred. The dossier is
self-contained even when it cites council report identifiers.

### 3. Tighten `magi-deliberator`

Keep the existing restricted frontmatter and shared agent type. Define two modes.

#### Independent opinion

The initial assignment contains the common dossier and one role charter. The
agent does not inspect or request peer conclusions. It returns:

```text
## Verdict
approve | reject | escalate

## Argument
## Evidence
## Assumptions
## Risks
## Alternatives
## Reversal conditions
## Confidence
```

Evidence cites repository paths, URLs, specifications, or common-dossier labels.
Inferences are marked and confidence is justified by evidence coverage.

#### Cross-examination

The follow-up supplies the other available first reports verbatim and identifies
their source agents. The agent applies its original charter and replies to
MAGI-CORE through `hub send` with:

```text
## Strongest opposing argument
## Weak or unsupported claim
## Missing evidence
## Most likely reversal condition
## Final verdict
## Confidence
```

The final verdict states whether the initial verdict was revised or affirmed and
why. The agent does not contact another council member or initiate another round.

### 4. Remove the standalone path

After the v2 command and agents exist:

1. remove `bin/magi`;
2. remove `omp/magi/MAGI.md`;
3. remove `omp/magi/magi.config.yml`; and
4. update only references that would otherwise be broken.

Do not retain redirect scripts, compatibility prompts, copied settings, or
deprecated aliases.

### 5. Run one final smoke check

Load `omp/magi` into an ordinary interactive host session. During an active host
turn, invoke `/magi` on a small, evidence-resolvable decision and confirm that the
active turn finishes before the injected MAGI prompt runs. Confirm the final
implementation exhibits:

```text
Main
  MAGI-CORE
    MELCHIOR
    BALTHASAR
    CASPER
```

Observe that:

- the command invokes `magi-core` in the current session;
- invocation during streaming queues a follow-up instead of steering or interrupting;
- MAGI-CORE dispatches exactly three independent first opinions in one batch;
- every cross-examination message contains the other complete first reports;
- exactly one peer-informed revision round occurs;
- the host receives one concise advisory dossier; and
- no MAGI component implements or mutates the target system.

Do not add prompt snapshots, mocked extension plumbing, exhaustive terminal-state
scenarios, sync/async matrices, or failure-injection tests.

## Completion criteria

Implementation is complete when:

- `/magi` invokes deliberation in the current host session;
- invocation during an active turn waits for that turn to finish;
- the host passes bounded context rather than a transcript dump;
- MAGI-CORE can spawn only `magi-deliberator` and council members cannot delegate;
- three independent first opinions form in one batch;
- one and only one peer-informed revision round occurs;
- peer reports are supplied verbatim rather than reread from mutable artifacts;
- the final dossier is concise, self-contained, and advisory;
- MAGI remains read-only;
- the standalone launcher, prompt, and config are removed without shims; and
- the final real-session smoke check succeeds.

## After-action report

Implemented on branch `magi-v2-implementation` (commit `bac27ca`).

### Delivered as planned

- `/magi` extension command in `index.ts` that injects a bounded host prompt via
  `sendUserMessage(deliverAs: "followUp")`; no automatic hooks, no spawning from
  extension code.
- New `magi-core.md` coordinator and reworked `magi-deliberator.md` (independent
  opinion + cross-examination modes) with the frontmatter the spec prescribes.
- Removed `bin/magi`, `MAGI.md`, and `magi.config.yml` with no shims. No config
  overlay or `hub` policy was added; `task.batch=true` stayed a host prerequisite
  (supplied only as an uncommitted smoke-test overlay).

### Finding: cross-examination addressing bug (found in smoke testing, fixed)

The first full smoke run produced a dossier on a **failed** cross-examination.
MAGI-CORE addressed council members by bare role names (`hub send to: "MELCHIOR"`),
which fail with `Unknown agent` — deliberators register under parent-qualified,
possibly-suffixed ids (observed: `MAGI-CORE.MELCHIOR-retry`). The initial
`magi-core.md` rewrite had dropped v1's warning about using the real returned
ids. Fix: MAGI-CORE now resolves live peers with `hub` (`op: "list"`) and
addresses members by their actual dispatched ids; `magi-deliberator.md` replies to
the sender's real id. This restores the "exactly one peer-informed round"
invariant.

### Verification (real interactive sessions, `claude-sonnet-4-5`)

- `/magi` registers with its description; both agents are discovered and
  dispatchable.
- Mid-turn `/magi` queues behind the active turn (follow-up ordering, not a steer).
- Topology: host -> `MAGI-CORE` -> one batch of MELCHIOR/BALTHASAR/CASPER.
- Post-fix cross-examination delivers (`woken` receipts), deliberators reply, and
  MAGI-CORE emits a complete `APPROVED_FOR_EXECUTION` dossier with initial->final
  verdicts and per-role report URIs.

### Residual notes

- `--model sonnet` fuzzy-resolves to the stale `claude-sonnet-4-0` (404 on this
